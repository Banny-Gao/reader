# 翻页这件小事：写给跨端阅读器的一些不成熟笔记

做阅读器这件事，最容易被低估的环节是分页。一个 App 的骨架、字体渲染、网络请求，两三天就能搭出一个跑得起来的版本；但要让一本三十万字的书在手机上刚好翻得舒服，让它落在平板上时不至于一行只剩十几个字，还要照顾横屏、系统字号、深色模式、用户手动缩放，这一堆问题没有捷径。我的意思是，捷径通常都能让你在演示时看起来不错，然后在第三章开始出问题。

这篇文章是一些零散的笔记，不试图给出"最佳方案"。更多是把我在做夸克阅读这类跨端阅读器时踩过的坑、验证过的经验、以及暂时没想通的问题写下来。排版引擎、文本测量时机、手势冲突、动效性能预算，这些题目每一个都够写一篇长文，我只能从一个比较窄的切口进入：读者翻页的那一刻，屏幕上究竟发生了什么。

## 一、先讲一个也许过时的前提

翻页本身并不是必要的。今天所有的阅读器都可以用滚动替代它，滚动条能给出精确的位置感，长按还能唤出系统级的滚动预览，甚至连进度都可以直接拖。翻页能活下来的理由，恰恰不在功能，而在它模拟了一种身体记忆——纸书的读者翻到下一页，是用手指捏住书页的右下角，然后手腕一甩。屏幕上的翻页动作虽然粗糙，但它保留了这个动作的意图。

这意味着我们其实是在做一件有点奢侈的事：为了还原一个不完全真实的物理隐喻，去牺牲一部分信息密度和可访问性。我的经验是，只要这种牺牲不越过两条线，它就是划算的。第一，翻页不能成为唯一的前进方式，滚动、章节跳转、进度条、目录都必须可用；第二，翻页不能破坏文本的连续性，比如不能让读者在翻过去之后发现自己的位置丢失了。~~如果哪次改版把这两条线越过了，我建议直接回滚，不要试图用动效去补救。~~

> 动效能掩盖信息问题，但掩盖不了信息问题。它只会让 bug 变得更好看。

后面所有的技术讨论，都建立在这个前提之上：我们承认翻页是一种模拟，因此我们可以理直气壮地做简化，也可以理直气壮地在简化失效的时候关掉它。

![一页纸的版心示意，标注了行宽、行高与页边距的关系](https://picsum.photos/seed/reader/600/400)

### 1.1 一次翻页应该包含哪些工作

把翻页拆开看，它其实是六件事的串行组合，而工程上的坑几乎都出在它们的接缝处。

1. 感知手势，判断这是"翻页"还是"选择文本"还是"回退"
2. 确定目标页的位置，向上还是向下，翻几页
3. 触发重排，重新测量并切分内容
4. 生成过渡帧，把两页之间的关系表达出来
5. 在过渡进行时处理并发输入，比如连点、拖拽中途反向
6. 结算状态，写入进度、更新时间戳、必要时同步到云端

第 1 步和第 2 步属于输入层，第 3 步属于排版层，第 4、5 步属于表现层，第 6 步属于状态层。跨端阅读器最麻烦的地方在于，这六步分别跑在不同的线程甚至不同的进程里：网页端的手势可能在主线程，测量可能落在 Web Worker，原生的翻页动画可能在合成线程，进度写入可能还排在一个异步队列后面。任何一个环节慢下来，用户看到的就是"翻不动"。

## 二、排版：让文字在屏幕上站稳

排版是分页的地基。地基歪一点，上面盖得再精致也晃。

### 2.1 行高：一个被滥用也最容易被滥用的参数

中文正文的行高，业界常用的经验值是字号的一点五到一点八倍。这个区间我不打算挑战，它是从铅字时代留下来的、在中文里被反复验证过的数字。真正的问题在于很多实现把它写成了**固定倍数**，而不是同时受制于字号缩放、行宽和语言。

当用户把系统字号调到最大，同一段文字的字号放大了一点四倍，而行高如果仍然是"一点六倍字号"，那么段落之间的相对呼吸就完全变了：一段话看起来像被挤在一起，而段与段之间又显得过远。反过来在超长行的场景里，一点五倍行高又显得过于松散，眼睛从一行末尾跳到下一行开头的成本变高。比较稳妥的做法是把行高定义成两段式：基准倍数乘以字号，再加一个随版心宽度增长的修正项。

```css
.reader {
  /* 基准行高：中文正文 1.72，接近铅字时代的中文书籍 */
  --reader-leading-base: 1.72;
  /* 字号由用户设置与系统缩放共同决定，这里不做兜底 */
  --reader-font-size: 18px;

  font-size: var(--reader-font-size);
  line-height: var(--reader-leading-base);

  /* 版心越宽，行高需要略微收紧，否则回扫成本太高 */
  line-height: calc(
    var(--reader-leading-base) -
    max(0px, (100% - 38em) * 0.004)
  );
}

@media (prefers-color-scheme: dark) {
  .reader {
    /* 深色底上的字会显得更"重"，行高需要额外放一点点 */
    line-height: calc(var(--reader-leading-base) + 0.06);
  }
}
```

上面这段里的 `max()` 与 `calc()` 混用，在部分老旧 WebView 上有解析问题。我花了很长时间才发现，深色模式下的行高调整根本不需要那么精确，用一个类名切换已经足够了。**能用开关解决的分支，不要用算术解决。**

### 2.2 版心与行长：40 到 48 个字符的窗口

中文排版讲"行宽"，英文排版讲"measure"，指的是一行的长度上限。中文的推荐行长在 25 到 40 个全角字符之间，超出之后眼睛回扫到下一行行首的准确率会明显下降。但这个数字是相对的：在手机竖屏上，一行最多也就 15 到 18 个字，怎么算都不算宽，所以问题不在"是否超过上限"，而在"是否太窄"。

太窄的版心会带来另一种不适：段落被切得很碎，一段话五行的，每行都不到十个字，读者需要频繁地重新定位起点。我的处理方式是给版心设定一个**最小舒适字数**，低于这个值时放大字号，高于上限值时改为居中留白而不是拉满行宽。这样在平板横屏上，两侧会留下比较宽的白边，看起来像纸书的留白，反而比满屏长行舒服。

### 2.3 段间距、标点与首行缩进

段间距是个会被误伤的地方。多数渲染方案会把段间距设成 0.7 左右的字号倍数，但在中文书籍里，段首缩进两字符 + 零段间距的传统其实更好看，因为它让段落边界由文字本身承担，而不是由空白承担。夸克阅读里我们提供了一个开关，默认走零段间距，因为网页来源的文本段落之间常有大量空行，需要先做归一化，否则排出来的页面像是被撕碎的报纸。

- 段落间距建议做成 `0` 到 `1em` 的连续可调，步长 0.1em
- 首行缩进只作用于正文，不要作用到标题、引用和列表项
- 中文段落之间的空行需要在预处理阶段折叠为一个段落标记
- 全角空格和半角空格混排是分页错乱的重要来源，归一化时要保留全角空格作为"手动换行"语义

> 段落之间多出来的那一行空白，很多时候不是排版的意思，是原始数据的意思。

## 三、分页：把一条线切成叶子

如果说排版是地基，分页就是砌墙。砌墙的手艺体现在两件事上：什么时候切，以及切完之后两边是否都好看。

### 3.1 测量的时机，比测量的精度更重要

分页的核心动作是测量：一行能放下多少字，一段占多高，一个代码块有多高，图片的宽高比是多少。争议最大的是**什么时候测量**。三种常见策略各有代价：

- 排版时同步测量：准确，但阻塞主线程，长文档会卡
- 排版后异步测量：流畅，但拿到的是旧布局，翻页会跳
- 预排 + 增量修正：折中，但需要维护两份状态

我们最后选了第三种，理由是跨端场景下"跳一次"比"卡 80 毫秒"更伤。这一取舍的完整讨论散落在[排版引擎实现笔记](https://example.com/docs/pagination-engine)里，本文只保留结论。下面是排版器里最核心的一段逻辑，它负责在容器尺寸变化后重排，并把结果切成页。

```ts
export interface PageBox {
  /** 在原文档中的起始偏移量 */
  start: number;
  /** 在原文档中的结束偏移量 */
  end: number;
  /** 该页内容在逻辑坐标系里的纵向偏移 */
  top: number;
}

export interface LayoutResult {
  pages: PageBox[];
  /** 整篇文档在当前排版下的总高度 */
  totalHeight: number;
  /** 排版时使用的容器指纹，失效则结果不可用 */
  signature: string;
}

function makeSignature(size: Size, settings: ReaderSettings): string {
  const parts = [
    Math.round(size.width),
    Math.round(size.height),
    settings.fontSize,
    settings.leading,
    settings.paragraphGap,
    settings.scale,
    settings.justify,
  ];
  return parts.join(':');
}

function relayout(doc: Doc, size: Size, settings: ReaderSettings): LayoutResult {
  const signature = makeSignature(size, settings);
  const cached = layoutCache.get(doc.id, signature);
  if (cached) return cached;

  const pages: PageBox[] = [];
  const pageHeight = size.height - settings.paddingTop - settings.paddingBottom;
  const blocks = doc.blocks;

  let cursor = 0;
  let pageTop = 0;
  while (cursor < blocks.length) {
    const box = takeBlock(blocks, cursor, pageHeight - pageTop, size, settings);
    if (!box) break;
    pages.push({ start: box.start, end: box.end, top: pageTop });
    pageTop += box.height;
    cursor = box.next;
    if (box.overflowed) {
      pageTop = 0;
    }
  }

  const result: LayoutResult = { pages, totalHeight: pageTop, signature };
  layoutCache.put(doc.id, signature, result);
  return result;
}
```

这段代码里藏着两个妥协。第一，`takeBlock` 对超过整页高度的内容会返回 `overflowed`，此时我们放弃精确的 `top` 偏移，只保证顺序——这意味着长代码块会被强行切页，而不会被切割成两半。第二，缓存的键包含容器尺寸的**四舍五入值**，这在平滑拖拽缩放时会产生大量缓存条目，我在 `layoutCache` 里做了 LRU 上限，代价是快速来回拖动缩放条时偶尔重排。

### 3.2 孤行、寡行与被遗弃的标题

排版学里有一整套专门处理"坏行"的概念，最常见的是寡行和孤行：段落最后一行只有一两个字孤零零躺在版心底部，或者段落第一行只有一个字被甩到上一节末尾。中文排版传统其实对这两个问题不太敏感，因为中文没有西文那种巨大的词间空隙来提示断行，但一旦做两端对齐（justify），问题立刻会暴露出来：为了让右边缘齐平，一个两个字宽度不同的段落，词间距会被拉伸得很难看。

我的处理顺序是这样的：先允许段落自然结束，不追求完美；只有当出现寡行或孤行时才尝试轻微调整——比如把段落整体上移一行，或者把这一行的字符间距压缩不超过 0.02em。超过这个阈值，宁可留下坏行。相关参数在配置里是：

- `widowOrphanTolerance`：容忍的坏行数量，默认 0
- `justifyThreshold`：行内拉伸超过该比例就放弃两端对齐
- `orphanAdjust`：是否允许为消除寡行而多占一行高度

更棘手的是标题。一级二级标题通常跟着一段正文走，如果标题出现在一页的末尾、正文被翻到下一页，读者会觉得页面"没写完"。理想的处理是把标题和它后面的第一段作为**吸附组**，宁可让第一页少放几行。实现上并不难，但它会打乱我原本的"高度累加"逻辑，导致每一页都要回看前一个节点，这就是分页算法复杂度上升的来源之一。

### 3.3 图文混排：一段不能被切开的麻烦

图片的排版是最容易破坏分页连续性的东西。行内图片和段内图片随文字流走，可以被自然切开；但独占一行的块图必须整体换行，如果它的高度超过一整页的正文区，就只能缩放到能放下为止。这里有一个常见错误：按原始像素高度渲染，导致手机上永远放不下。正确做法是先算可用高度，再等比缩放，最后才居中。

![一块独占整行的插图，下方是图注，图注属于同一段落不可被分页切开](https://picsum.photos/seed/reader/600/400)

图注的处理比图本身麻烦。我的约定是：块图和它的图注绑定成一个组，组内不允许拆分；如果组整体放不下，就整组推到下一页。如果连续三页都放不下，说明容器太窄，此时降级为"图缩到版心宽度、图注单独成段"。这个降级逻辑后来被复用到表格和数学公式上，算是意外收获。

### 3.4 一份看起来很正经的分页配置

分页相关的参数最终都收敛到一个配置对象里，下面是删减过的版本：

```json
{
  "pagination": {
    "mode": "paged",
    "pageTurnStyle": "curl",
    "respectSystemFontScale": true,
    "columns": 1,
    "padding": { "top": 24, "bottom": 32, "left": 20, "right": 20 },
    "snapToParagraph": false,
    "minLinesPerPage": 4,
    "orphanControl": true,
    "blockScaling": {
      "image": "fit-width",
      "code": "scroll-to-next-page",
      "table": "scaled"
    }
  },
  "gesture": {
    "edgeThresholdPx": 24,
    "dragFollow": true,
    "conflictWithSelection": "gesture-wins-above-8dp"
  },
  "motion": {
    "durationMs": 320,
    "reducedMotion": "fallback-to-slide"
  }
}
```

`code: "scroll-to-next-page"` 是我后来加的：代码块如果超过一页高度，就把它当做一个独立的滚动区域，手指在它上面滑动时先滚代码，滚到底了才翻页。听起来自然，实现起来却很别扭，因为翻页的滚动容器和代码块的滚动容器会抢事件。

## 四、手势：读者如何说出"翻到下一页"

### 4.1 三种输入的分工

翻页手势实际上承担了三种语义：**空间语义**（往前走还是往回走）、**速度语义**（轻轻翻还是快速甩）、**连续语义**（我还在这一页里吗）。传统纸书把这三种都压缩进了一个动作里，屏幕上做不到，只能靠不同的手势分别承担。

- 点击页面左侧三分之一的区域：上一页；右侧：下一页；中间：唤出菜单
- 从屏幕边缘向内拖拽：翻页，带跟手预览
- 屏幕中央下滑：唤出目录与设置
- 长按：选中文字，进入选区状态
- 方向键 / 空格：键盘用户的等价路径，在桌面端不可省略

这里的坑在于**长按和拖拽的冲突**。二者的手势起点几乎一样，区别只在位移和时间。经验值是：位移超过 8dp 判定为拖拽，时间超过 350 毫秒且位移小于 8dp 判定为长按。但这个阈值在高 DPI 屏幕上要做密度换算，否则在 3x 屏上 8dp 等于 24 个物理像素，用户会觉得"怎么稍微一动就变成拖拽了"。

判定顺序上，我一般按下面这套来跑，先排除最不可能的情况，再做耗时判断。

1. 触点落在选区把手附近：直接判定为调整选区，结束
2. 累计位移超过 8dp：判定为拖拽，交给翻页或滚动
3. 累计位移不足且按压超过 350 毫秒：判定为长按，交给选区
4. 以上都不满足：抬手时判定为点击，走点击热区

把"落在把手上"放在第一步，是因为它是唯一不可逆的操作——一旦进入了选区调整，再想退回翻页状态需要额外清理，代价远高于其他几种。所以宁可让少数明显是翻页意图的触摸被误判为选区调整，也不要反过来。

### 4.2 边界区域与误触成本

边缘点击是效率最高的翻页方式，也是误触的重灾区。手持设备时，拇指在屏幕下缘或侧缘的落点非常密集，如果把"点击左三分之一 = 上一页"做满整列，手指自然落点区域就会频繁触发误翻。

我见过的最好的处理不是缩小响应区域，而是**给误翻加代价**：一次误翻再翻回来，代价很低；但如果误翻触发了动效，读者要等 300 多毫秒，这 300 毫秒的心理成本远大于点错本身。所以后来的版本里，误触区域的翻页动效被降级成 120 毫秒的位移过渡，而点击响应区中间的部分保留完整的翻页动效。关于响应区域怎么切才不反直觉，[手势热区设计笔记](https://example.com/notes/gesture-hotzones)里有更细的图。

> 交互的成本不只由"操作是否可达"决定，还由"出错之后能不能低成本撤销"决定。

### 4.3 手势和滚动不是一回事

滚动有惯性、有连续位置、有精确的进度语义，翻页没有。把两者混为一谈是最常见的架构错误：用一个 `scrollTop` 去驱动分页，翻页时会抖，因为 `scrollTop` 是浮点数且会被浏览器平滑处理。

```ts
// 错误示范：用一个滚动位置同时表达"第几页"和"正在翻第几页"
// scrollTop 在拖拽过程中会被系统平滑，页码会来回跳
function onScroll(e: Event) {
  const el = e.target as HTMLElement;
  const index = Math.round(el.scrollTop / el.clientHeight);
  goToPage(index);
}

// 正确做法：页码是离散的，拖拽过程是连续的，两者分开表达
interface TurnState {
  current: number;      // 离散页码
  dragging: boolean;    // 是否处于拖拽中
  progress: number;     // 0..1 的跟手进度，不参与页码计算
  velocity: number;     // px/s，用于判断甩动
}

function settle(state: TurnState, threshold = 0.35) {
  const forward = state.progress > threshold || state.velocity > 900;
  const backward = state.progress < -threshold || state.velocity < -900;
  if (forward) state.current += 1;
  else if (backward) state.current -= 1;
  state.progress = 0;
  state.dragging = false;
}
```

顺带一提，`goToPage` 在错误示范里被放在了滚动回调中，这在真实项目里会导致一次滚动触发几十次排版，是典型的性能陷阱。

### 4.4 构建与验证

这类交互很难靠肉眼看代码验证，我一般会跑一套自动化的截图对比：

```bash
# 打开一个带全部语法元素的测试文档，跑分页稳定性快照
npm run test:pagination -- --doc fixtures/kitchen-sink.md --shots 42

# 对比分页结果与上一次基线，任何一页的行数变化都会失败
npm run test:pagination -- --baseline fixtures/baseline.json --fail-fast

# 检查是否有孤行、寡行、溢出容器的内容
npm run lint:layout -- --rule no-orphan,no-overflow,min-lines=4
```

第二个命令是我最常用的。分页算法的改动往往只影响一两页，人工翻阅三十页找问题太慢，基线对比能把这个过程压缩到几秒。代价是基线文件经常变脏，需要在提交信息里说明"哪一页因为什么改变了"。~~如果基线每次都全量更新，那这条测试就等于没写。~~ 这条经验在[分页回归测试实践](https://example.com/posts/pagination-regression)里被反复提到。

## 五、动效：把时间当作一种材质

### 5.1 曲线不是玄学

翻页动效的时长和曲线是最容易被拍脑袋决定的参数，也是最影响主观感受的。我的起点是一个粗暴的经验：翻页时长不应该短于页面横移距离除以某个"看起来不着急"的速度，也不应该长到让读者等待。实际落地的区间是 280 到 360 毫秒，曲线用一个轻微的减速收尾。

```css
.page {
  will-change: transform;
  transform: translate3d(0, 0, 0);
  transition: transform 320ms cubic-bezier(0.22, 0.61, 0.36, 1);
}

/* 跟手阶段不启用 transition，由 JS 逐帧写入 */
.page.is-dragging {
  transition: none;
}

.page.is-back {
  transform: translate3d(-100%, 0, 0);
}

@media (prefers-reduced-motion: reduce) {
  .page {
    transition-duration: 1ms;
  }
}
```

注意 `will-change` 不应该常开。它会一直占用合成层内存，在低端机上同时存在三个 `will-change: transform` 的元素就足以让掉帧掉到不可接受。我的做法是在手势开始时才加类，动画结束后立刻移除。

### 5.2 三种翻页形态的取舍

- **横向位移**：最稳，跨端一致性最好，性能开销最低，但物理隐喻最弱
- **仿真翻页**：在 Android 上接近真实纸张，代价是每帧都要重新绘制，两三个长章节页能明显掉帧
- **立体旋转（Y 轴）**：介于两者之间，视觉上"像翻书"，实现上只是一个 3D 变换 + 阴影遮罩

最后我们默认用横向位移，把仿真翻页做成设置项，并且只在低端设备检测结果为"高性能"时才开放。这个判断的依据是一段三十秒的性能探针：连续翻页三十次，记录帧间隔的中位数和九十分位数。中位数低于 16 毫秒但九十分位数高于 32 毫秒的设备，一律走简化动效。

### 5.3 动效里的隐藏状态

还有一个容易忽略的问题：翻页动画进行中，页面的高度可能因为安全区、状态栏、或者键盘弹出而变化。如果不冻结，动画结束的瞬间会出现一次布局跳动，读者会以为"页面自己缩了一下"。解决办法是在动效期间锁住容器的尺寸，把所有会变化的东西提前算好。

## 六、跨端：同一本书的三种容器

### 6.1 设备差异先于设计

跨端一致性最容易犯的错，是先定一套设计稿再往各个端上套。实际上应该反过来：先承认三个端的能力差异，再找最小的公共子集。

- 手机竖屏：一页 15 到 18 字，拇指操作区在下缘，需要下划手势呼出菜单
- 平板横屏：一页 30 字以上，触控笔与键盘都可能存在，需要悬停态和快捷键
- 桌面浏览器：窗口任意大小，缩放由用户控制，需要处理无限重排和内存回收

三个端在排版上的共同点只有一个：**行高和字号的相对关系必须一致**。如果手机上字号 18、行高 1.72，平板上变成 22 和 1.6，读者会觉得"这本电子书在平板上排得很挤"。宁可让字号差得大一点，也要保持比值一致。

### 6.2 缩放与内容宽度

桌面端有一个手机端没有的问题：用户拖拽缩放条时，容器尺寸每一帧都在变。如果按 3.1 里的策略做，缓存会被冲垮，体验就是连续掉帧。我的处理是分两级——拖拽过程中只做**估算排版**，用平均字符宽度快速算出页数，保证页码和滚动条是稳定的；松手后再做精确排版，把页面内容替换成精确结果。估算排版和精确排版的页数差异通常在三页以内，读者几乎察觉不到。

### 6.3 书脊：进度感的另一种表达

书脊这个词在电子阅读里用得不多，但很多人对它的印象来自 Kindle 那一代：在右侧排一列极窄的缩略条，标出当前阅读位置和全书章节。这个设计今天依然有价值，因为它解决的是滚动和翻页都解决不了的问题——**读者在书里有多深**。

- 书脊在手机上可以退化成顶部一条 2 像素的进度线
- 在平板上可以做成右侧的真实缩略条，支持点击跳转
- 在桌面端可以做成顶部的一排章节标签

需要注意的是，书脊跳转之后必须把选区状态一起处理。读者从第 3 页跳到第 200 页，之前在第 3 页高亮的段落就不应该再高亮；反过来，如果读者在第 200 页做了选区并且生成了注释，返回到第 3 页时也不该有残留。我见过的 bug 里，有一半是"状态没清理"，而不是"状态没算对"。想更系统地整理这类问题，可以对照[阅读器状态机检查清单](https://example.com/wiki/reader-state-machine)逐条过一遍。

### 6.4 一致的是模型，不一定是像素

跨端最终能对齐的是**数据模型**：分页结果的描述、进度表示为"第几章第几页"还是"文档偏移量"、选区表示为绝对偏移还是行列号。对齐了模型，像素就可以各自发挥。反过来，如果一开始就要求三端像素一致，桌面端那个可以任意缩放的窗口会成为噩梦。

## 七、选区：读者留下的痕迹

选区是阅读器里最容易被当成"编辑器功能"来做的地方，结果就是各种别扭：长按弹出的菜单太大、拖动把手太细、选区高亮在翻页之后消失、注释跟着选区一起被翻页动画拉扯变形。

我的处理原则有三条。第一，**选区优先于翻页**：手势起始在选区把手附近时，一律判定为调整选区，不参与翻页判定。第二，**选区在跨页时要可视化**：一段话跨了两页，两页都要显示高亮的对应部分，哪怕右侧只剩两个字。第三，**选区与注释分离**：注释是持久数据，选区是临时状态，注释锚点必须锚在文档偏移上，不能锚在页码上。

![高亮的选区跨越页面边界，左右两侧分别显示半透明色块](https://picsum.photos/seed/reader/600/400)

第三条尤其重要，因为我见过太多应用把页码当锚点。读者在第 12 页做的注释，读者在第 13 页修改字号之后应该还在同一句话上，而不是跳到别的地方去。翻页只是视图，文档偏移才是数据。

> 如果你的阅读器有一个功能需要靠"回到原来那一页"来实现，那这个功能设计得就不对。

## 八、几个还没想清楚的问题

写到最后，我想诚实地列出几个至今没有好答案的问题。

第一，**两端不同步时以哪端为准**。手机翻到第 50 页，平板上还停在第 12 页，是把平板拉过来，还是提示冲突？我目前的做法是同一设备上的多标签页用最后一次操作覆盖，跨设备则保留两端各自的进度，等读者主动打开另一端时再询问。这个策略显然回避了真正的多端同步问题。

第二，**不同字体的分页差异**。同一份文本换一种字体，页数可能差百分之十以上。如果用户是在打开书的时候选的字体，那没问题；但如果是阅读中途切换，要不要保留原页码？保留意味着新页码上可能有不同的内容，不保留意味着读者要重新找位置。

第三，**仿真翻页的性能天花板**。我在中端安卓机上试过用 Skia 直接画纸张卷曲，单帧耗时能压到 8 毫秒，但在同一台机器上跑三个小时之后，内存会稳定增长，最后触发一次明显的卡顿。我怀疑是纹理缓存没有回收，但一直没定位到具体是哪条路径。

第四，**两端翻页的手感能不能统一**。物理隐喻本身带着硬件的重量，手机的翻转和桌面鼠标的拖拽在"力度"这个维度上完全不同。硬要统一，就必须放弃一部分物理感；不统一，就必须接受两套手感、两种动效曲线、两套参数。

这四个问题我都还没有满意的答案。也许其中有些是应该交给读者去配置的，而不是由产品替他决定的——这大概也是设置页越做越长的原因。

> 好的阅读器不是替你做决定，而是让每个决定的后果都足够轻。

如果要我给刚开始做分页的人一句话的建议，那就是：先写一个笨到极致的分页器，把每一行都硬塞进固定数量的行框里，能跑通翻页、翻页进度和翻页恢复，然后**再**一行一行地往里面加孤行控制、吸附组、跟手预览。多数团队跳过第一步，然后花三周在一个建立在不可靠的地基上的架构里调参数。

我在这条路上还在半山腰。上面这些笔记，与其说是结论，不如说是一份给未来的自己的检查清单：如果哪天我要重写一次分页器，我希望先想起这些坑。
